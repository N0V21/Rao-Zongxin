# 上海落户政策 RAG（baseline v0.4）

一个**只依据政府公开原文作答**的上海落户政策问答基线系统。
核心目标不是"答得多"，而是**不编**：材料里没有的，明确拒答。

- 检索：`BAAI/bge-small-zh-v1.5` 向量召回 + 查询改写，条款级（`##`）切分
- 生成：任意 OpenAI 兼容接口（默认 DeepSeek），`temperature=0`
- 语料：4 份现行有效文件，49 个条款，全部带文号、生效日期与 PDF 快照

---

## 快速开始

```bash
# 1. 依赖（建议 Python 3.10+）
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. 密钥
cp .env.example .env      # 然后填入你的 LLM_API_KEY

# 3. 交互问答
python main.py
```

首次运行会自动下载 `bge-small-zh-v1.5`（约 100MB），之后走本地缓存。

### 批量评测

```bash
python eval/run_eval.py    # 结果写入 results/baseline_v0.jsonl
```

### 测试（不联网、不需要密钥）

```bash
pytest -q
```

## 数据格式

`data/` 下文件命名为 `NN_标题.md`，顶部是 YAML front-matter：

```yaml
---
id: sh-hukou-talent-2025
title: 上海市引进人才申办本市常住户口办法
doc_no: 沪府规〔2025〕8号
issued_date: 2025-11-21
effective_date: 2025-12-01
expire_date: 2030-11-30
source_url: https://www.shanghai.gov.cn/...
raw_snapshot: 上海市人民政府关于印发....pdf
status: effective        # effective | superseded | draft
---
```

切分规则：第一个 `# ` 是**文档名**（进入每条 chunk 的检索文本），
每个 `## ` 是**一个条款**。标题上方/下方的说明性文字归为"前言"，
标记 `is_article=False`，默认不参与检索（避免印发通知污染召回）。

新增文件只需丢进 `data/`，无需改代码。详见 [data_card.md](data_card.md)。

## 相比 v0.3 修掉了什么

原 `main.py` 可以跑通，但有几处会**静默影响效果**的问题，已逐条修复并加了回归测试。

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | `rewrite()` 引用不存在的 `_REWRITE_RULES`，且从未被调用 | 整套查询改写是死代码；一调用就 `NameError` | 规则修正为 `REWRITE_RULES` 并真正接入检索（多变体取最高分） |
| 2 | 切分时首个 `# ` 标题被 `buf = seg.lstrip()` 覆盖丢弃 | **53 个 chunk 中 40 个**的检索文本不含文档名，"居转户"只能靠语义硬猜 | H1 提取为 `doc_title`，拼进每个 chunk 的 `search_text` |
| 3 | 每轮提问都重新 `model.encode` 全部 chunk | 交互问答每问多花数秒 | 一次建索引，矩阵缓存到 `.cache/` |
| 4 | 邻条款以字符串拼接进 `context`，命中相邻条目时高度重复 | 白烧 token（baseline 第 3 题 5407 tokens） | 按条款序构造窗口，并用区间合并去重；被并入的条目换成一行指针 |
| 5 | `front-matter` 用非贪婪正则删除，正文含 `---` 会误伤；元数据被丢弃 | 文号/生效日期拿不到，无法做版本消歧 | 仅在文件开头精确切分，并用 PyYAML 解析保留元数据 |
| 6 | 01 号文的印发通知被切成 chunk 参与检索 | 污染"由谁提交/怎么办理"类问题 | 标记为非条款，默认排除 |
| 7 | 空答案被评测记为 `hit` | **虚高指标**：baseline 10 题里 4 题答案为空 | `Generation.empty` 显式标记，评测单独统计 |
| 8 | Hit@3 用含不可答题的总数作分母 | 指标被系统性低估（6/10 而非 6/7） | 区分可答题与不可答题分别统计 |
| 9 | `LLM_MODEL=deepseek-flash`，model 名不存在 | 部分请求返回空内容 | `.env.example` 改为 `deepseek-chat`；空返回会被显式报警 |
| 10 | API Key 明文写在 `.env` 里且 `.env` 曾被误提交风险 | 密钥泄露 | 改用 `.env.example`；`.gitignore` 覆盖 `.env`、`.cache/`、`__pycache__/` |
| 11 | **查询改写把"文档全名"当独立查询注入** | 无关条款拿到 0.91 高分，把含答案的条款挤出前排 | 变体改为短关键词注入 + `VARIANT_WEIGHT=0.9` 折扣加权 |
| 12 | `GOLD` 把"公示期是多少天？"标成 `None`（应拒答） | 标错题：03 号文六.3 写明"为期 5 天的网上公示"，答对反而记成 ok-refused | 改标 `["03_"]`，该题实为可答题 |
| 13 | 上下文窗口用**跨文件全局下标**计算 | 01 号文的命中会带出 02 号文的条款（两份都有"第五条"），误导模型并使"出处"标注失效 | 窗口严格限定在单文件内，去重也按文件独立处理 |

> `results/baseline_v0.legacy-v0.3.jsonl` 是**修复前**的原始评测输出，保留作对照：
> 表面 6/10 hit，实际 4 条答案为空，且 5 道标为"应拒答"的题里有 1 题其实可答。

### 本次改动后的实测（仅检索层，未调用 LLM）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 可答题检索 Hit@3 | 6/6（但含 4 条空答案） | **7/7** |
| 不可答题最高 top1 分 | 0.69 | 0.82（`公示期`，见下） |
| "居转户"错误条款得分 | 0.913（02 号文第二条，无关） | 0.730（03 号文激励条件，正确） |
| 每问重复编码 | 每轮 53 条全量重算 | 建索引一次 + 磁盘缓存 |
| 单问检索耗时 | ~2–6s | **0.01–1.5s**（首次含预热） |
| TOP-10 上下文 | 30 段，含大量重复；且窗口跨文件 | 去重后按区间合并，严格限定在本文件内 |
| 同题 prompt 字符数 | — | 2112–8563（约 1.3k–5.4k tokens） |

> ⚠️ 注意 `公示期是多少天？` 一次 top3 里 03 号文仅以 **0.816 vs 0.822** 险胜，
> 排在第 3 位。这类"两个文件都提过该词、只有一处写了天数"的问题，
> 是当前向量召回最脆弱的地方，需要重排才能稳定。
>
> 另：01 号文与 02 号文都有"第五条（申办条件）"等同名标题，
> 这正是"上下文窗口必须限定在单文件内"的原因——跨文件拼接会直接误导模型。

## 已知局限

- **拒答靠 prompt 而非硬闸门**：`SCORE_THRESHOLD` 只是启发式兜底。
  实测三个应拒答问题得分 0.54~0.82，全都高于 0.5，说明单靠相似度阈值
  拦不住无关问题（"公示期"甚至比多数可答题分更高）。
  真正的拒答来自 prompt 约束 + `REFUSE_MARKERS` 复核。
  若要更可靠，应引入 cross-encoder 重排，或让模型先输出"材料是否包含答案"。
- **时效过滤未接入**：`status` / `effective_date` 已解析进元数据，
  但检索仍会召回历史版本条款（data_card 列出的"时效冲突"缺陷尚未闭环）。
- **多条件合取问题**：如"学历 + 院校排名 + 社保时长"需要跨 chunk 组装，
  目前仅靠 `context_window=1` 的邻条扩展，未做显式聚合。
- **悬空引用**："详见本市紧缺急需人才目录"这类条款正文没有名单，只能拒答。
- **公示期类问题召回不稳**：正确答案仅以微弱分差进入 top3（见上表），
  依赖 top-k 足够大（默认 `TOP_K=10`）。
- 语料只有 4 份文件，**不构成完整的上海落户政策库**，不应用于真实办事决策。
- 空答案检测只覆盖"content 为空"；若模型答非所问，仍需人工或 LLM-as-judge 评估。
